# Автономная работа и расход ресурсов

В меню сессии включите «Работать автономно до завершения цели» и укажите задачу. Можно попросить агента работать автономно прямо в разговоре: ему доступен `session_autonomy`. Простое обсуждение этой функции режим не включает.

| Событие | Поведение |
| --- | --- |
| Завершился очередной ответ | Ядро создаёт следующий внутренний запуск по той же цели |
| В очереди есть сообщения пользователя | Они выполняются раньше автоматического продолжения |
| Цель выполнена | Агент отмечает `complete` с результатом; цикл заканчивается |
| Нужны недоступные данные или решение вне разрешённой задачи | `blocked` с причиной; без выдуманного согласия пользователя |
| Ожидание порученной работы | `wait`; результат подсессии пробуждает цель |
| Stop / приоритетное прерывание | Автономия и обычная очередь ставятся на паузу |
| Нет квоты | Сохраняется текущая работа; при включении автономии автоматически включается ожидание квоты |
| Окно закрыто / ядро обновляется | Цель, очередь и текущий независимый исполнитель сохраняются |

Внутреннее продолжение помечено как системное событие, а не вымышленное сообщение пользователя. Обычные вопросы о выборе обратимого решения получают явно обозначенную политику автономной работы; запросы разрешений и внешней авторизации не получают выдуманных ответов. Stop и выключение режима доступны с ноутбука и телефона.

На Windows активная автономная цель удерживает систему от автоматического сна через `SetThreadExecutionState`; экран может выключаться. Ручной сон, выключение и действие закрытия крышки не меняются. [Документация Windows](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate).

## Периодические задачи

В меню сессии → «Периодическая задача…» задайте интервал и текст одного прохода. Доступны секунды, минуты и часы, приостановка и выключение. Агент может настроить тот же механизм через `session_schedule(action=set, intervalSeconds=300, prompt=...)`, только по просьбе пользователя о повторяющейся работе.

Время следующего запуска хранится в SQLite. Раз в секунду ядро проверяет сроки независимо от модели. Каждый запуск выполняет один проход; непрерывная автономия при включении расписания отключается. После ошибки модели таймер остаётся активным и делает следующую попытку по расписанию. Если сессия занята, ждёт ответа, квоты или имеет очередь, повторные задания не накапливаются. После простоя пропущенные интервалы объединяются в один запуск. Служебные пробуждения записываются как системные сообщения, а не новые слова пользователя.

Stop и «Сейчас» приостанавливают расписание вместе с очередью. Обычные сообщения сохраняются; ожидающее автоматическое пробуждение отменяется. Явное продолжение очереди или включение расписания возвращает таймер. Окно можно закрыть: таймер принадлежит ядру, переживает его обновление и перезапуск. При выключенном компьютере или остановленном ядре запусков нет; после возвращения выполняется один просроченный проход. Активное расписание удерживает компьютер от автоматического сна по той же политике, что автономия.

## Полоски под названиями

Верхняя полоса — токены, нижняя — накопленное CPU-время. По уточнённому правилу доли проектов и сессий считаются от общего расхода, включая неактивные сессии; полоски проекта видны, когда он свёрнут. Подсказка содержит точное число учтённых токенов, CPU-секунды и обе доли. В статистике можно выбрать старый период и график токенов либо CPU.

В дереве настольного клиента полоски и точки привязаны к общим координатам списка, включая вложенные сессии. Работающая сессия подсвечивает также свой проект; точка проекта сообщает о вопросе или новом результате, с приоритетом вопроса. Состояние сворачивания проектов сохраняется отдельно для активного и неактивного списков и восстанавливается при запуске и горячей замене окна.

Текущий период начинается с последней известной границы автоматического или ручного сброса Codex. Токены берутся из счётчиков разговоров Tethium; это доля учтённого расхода, а не процент оставшегося лимита аккаунта. Если сведения о сбросе ещё не поступали, используется вся доступная история.

CPU — сумма процессорного времени, не мгновенная загрузка машины. Учёт начинается после установки этой версии. Ядро раз в 5 секунд спрашивает Windows само, одним системным вызовом и без дочерних процессов; в базе лежит одна сумма на сессию за период квоты (таблица `cpu_totals`), запись раз в 30 секунд. Графиков и прошлых периодов нет: только «с последнего сброса» и «всё время». Токены с разбивкой на вход, кэш, выход и рассуждения хранятся так же (`token_totals`), построчной истории нет. Полоски считают только вход без чтения из кэша плюс выход; окно статистики показывает полные цифры. Новая запись считается только при росте счётчика потока: поздняя или повторная не меняет сумму, а смена исполнителя действует на новые токены. Снимки PID + времени запуска предотвращают смешивание повторно использованных PID; новое ядро считает уже работающие процессы от их текущего значения, поэтому при замене ядра ничего не считается дважды. Включаются дерево исполнителя и дочерние процессы. Для общего Gradle daemon текущий клиент определяется по локальному TCP-соединению; несколько возможных владельцев или смена владельца между снимками не распределяются предположительно. Старый расход daemon до его подключения не приписывается сессии. Короткие процессы, завершившиеся между снимками, и неоднозначно связанные внешние сервисы могут быть пропущены.

## Просмотр документов

Markdown поддерживает таблицы GFM. Для каждой сессии запоминаются выбранный опубликованный или открытый вручную файл, открытое/закрытое состояние панели и ширина. Они восстанавливаются при возвращении в сессию и перезапуске окна.


Закрепить документ отдельным пунктом: контекстное меню проекта → «Закрепить файл в проекте…». Такой пункт открывает файл на всю рабочую область; разговор и исполнитель для него не создаются. Пункт можно переименовать и открепить; сам файл остаётся на диске.

Закрепить справа у обычной сессии: контекстное меню сессии → «Закрепить файл справа…», либо кнопка скрепки в панели уже открытого документа. При возвращении в сессию закреплённый файл открывается автоматически, даже если панель перед уходом закрывали. Повторное нажатие скрепки снимает закрепление. Настройка хранится у ядра и работает также в лёгком десктопном клиенте. Локальный выбор файла и путь на удалённом клиенте проверяются относительно проекта/рабочего каталога сессии.

HTML использует Chromium с отрисовкой в Swing (OSR), поэтому нативное дочернее окно браузера не перехватывает клавиатуру. Markdown отображается в том же браузере: таблицы GFM с компактными ячейками и локальные изображения с ограничением по ширине. Изображения из относительных и абсолютных путей встраиваются в документ, поэтому доступны также удалённому клиенту. При скрытии панели браузер освобождается; при возвращении документ загружается снова. Закрытие клиента и GL-поверхности завершается перед созданием следующего браузера. Проверка `gradlew focusProbe` использует реальные нажатия: ввод в поле, ввод в HTML, возврат, Ctrl+C / Ctrl+V, перезагрузка страницы с повторяющимся autofocus. Требуемые экспорты Java Desktop входят в оба пакета.

Проверка `gradlew gradleCpuProbe` запускает две настоящие Gradle-сборки с одним демоном, привязывает их к разным сессиям и проверяет CPU-записи демона для обоих владельцев. Демон пробы имеет отдельный JVM-маркер; после проверки завершается только он. Учёт поддерживает IPv4 и IPv6 loopback.


## Большая история

Десктоп и лёгкий клиент получают индекс сообщений и подгружают текст вокруг видимой области. Один HTML-документ содержит не более 12 фрагментов по 8000 символов, кэш ограничен 64 фрагментами. Длинное сообщение разбивается на части с пометкой «Продолжение». История в базе и контекст агента не сокращаются.

Обычный ползунок покрывает всю историю, включая ещё не загруженные участки. Их высота сначала оценивается, затем уточняется с сохранением места чтения. Выбор запроса, карта запросов и «В конец» работают со всей историей. При чтении старого сообщения новый ответ не переключает экран на конец. Старый полный API сохранён для совместимости с ранее установленными клиентами и Android.

## Неактивные проекты и корзина

Контекстное меню проекта → «В неактивные весь проект» перемещает его вместе с сессиями и закреплёнными файлами в нижний раздел. «Вернуть проект в активные» возвращает проект, сохраняя индивидуальные состояния сессий. Это изменение отображения; запуски и очередь продолжают работать.

«Удалить сессию…» в меню сессии требует подтверждения и убирает её из рабочего списка. История сохраняется; текущее исполнение не отменяется. Слева вверху кнопка ⋯ открывает «Настройки · корзина сессий»: там доступны восстановление и отдельное окончательное удаление с повторным подтверждением. Окончательное удаление блокируется, пока сессия или её подсессии работают. Удаляются записи и вложения Tethium; файлы проекта и самостоятельные подсессии сохраняются.

Проверки: `gradlew historyProbe` — 2400 сообщений, переходы по всей истории, поток ответа без сдвига старого места; `gradlew previewLifecycleProbe` — 20 переходов HTML/WebGL ↔ Markdown, таблицы и освобождение браузеров; `gradlew uxProbe` — рабочее окно, очередь и навигация.

## Дополнения интерфейса

Полоски ресурсов прямоугольные, по 2 пикселя, с промежутком 1 пиксель. Иконка проекта центрируется по всей высоте строки вместе с полосками.

«Сейчас» с пустым вводом отправляет через прерывание верхнее сообщение очереди: части, вложения и получатели поручений сохраняются. Остальная очередь остаётся на паузе. Ручная отметка «Требует внимания» в меню сессии сохраняется независимо от прочтения результата и снимается вручную.

Закрытие и снятие закрепления файла требуют подтверждения; сам файл не удаляется. У закреплённого документа отсутствует кнопка «Вернуться к чату».

Результаты инструментов Codex imageView и imageGeneration сохраняются отдельными снимками и показываются миниатюрами в истории ответа. Щелчок открывает изображение в панели результатов. Текст и миниатюры подгружаются теми же ограниченными страницами.

Для фоновых сервисов вне дерева исполнителя доступен инструмент `process_track` с PID: он сохраняет владельца и время старта процесса, учитывает его CPU и потомков после замены ядра. Это применяется и к повторно используемым помощникам. Учёт начинается с регистрации; старое незафиксированное CPU-время не восстанавливается предположительно.


## Отложенные задачи

У каждого проекта есть список задач на будущее. На строке сессии счётчик `[4]` показывает, сколько задач выполнится в ней. Проект показывает только то, чего не видно на строках сессий: всё, пока он свёрнут, а развёрнутый — например, задачи для новой или неактивной сессии. Так же и с точками внимания; по нему, по надписи «Отложено · N» рядом с очередью или через меню «Отложенные задачи…» открывается список. На Android: счётчики в списке проектов и «Отложено · N» рядом с очередью. В любой сессии достаточно сказать агенту «отложи это»: он вызовет `backlog_add` с текстом, понятным без этого разговора. Сам агент ничего не откладывает.

У задачи есть приоритет и условия запуска: квота от N% и свободный CPU от N%. Без своих условий действуют общие, по умолчанию 80% и 40%; значение 0 снимает условие. Квота — наименьший остаток среди окон исполнителя, который будет работать. Свободный CPU считается по самой высокой загрузке машины за последнюю минуту. Условия проверяются только при старте: начатая задача не прерывается, даже если квота потом просела. Новая задача с условием по CPU ждёт минуту после прошлого запуска, пока он не отразится в замере.

Одновременно идёт до 3 отложенных задач; число, условия по умолчанию и паузу автозапуска можно менять внизу окна списка. Работа человека важнее: задача начинается только в свободной сессии, без работы и очереди. «Запустить сейчас» не смотрит на условия и встаёт в очередь сессии.

Где выполнять, задаётся явно: по умолчанию в сессии, откуда отложили; как вариант — в общей сессии по имени, например «Мелкие задачи», она создаётся при первой необходимости; в виде исключения — в новой сессии. Завершённая задача уходит из списка. Упавшая или остановленная остаётся с пометкой, сама не перезапускается и при повторе идёт в той же сессии. В списке для каждой задачи написано, чего именно она ждёт.

## Ограничение CPU и персональные демоны

Настройки ⋯ слева → «CPU: общий лимит и приоритет…». По умолчанию исполнители вместе занимают не более 85% CPU ноутбука. В меню проекта и сессии доступны собственный потолок и приоритет; ноль означает наследование. Все проценты считаются от полной мощности компьютера, а родительские ограничения продолжают действовать. Приоритеты «Фоновый», «Обычный», «Важный» соответствуют Windows Idle, BelowNormal, Normal; это классы планирования, не гарантированные доли CPU. В подсказках строк показаны текущая нагрузка и действующий потолок. Полоски накопленного расхода остаются отдельной статистикой.

Windows Job Objects образуют цепочку общего бюджета, проекта и сессии. Новый исполнитель входит в свою группу до запуска CLI, дочерние процессы наследуют группу. Демоны остаются в ней после завершения ответа. Отдельный `JobKeeper` удерживает дескрипторы между запусками и при горячей замене ядра; файлы его исходной сборки тоже нужно сохранять, пока он работает. Установщик запускается управляющим ядром, вне бюджета текущего исполнителя. GUI и ядро не ограничиваются этим бюджетом; малый процесс хранителя входит в общий бюджет и закрепляет иерархию до присоединения задач. Ошибки присоединения существующих процессов выводятся в диалоге CPU, а не скрываются.

Для новых запусков у каждой сессии свой постоянный `session-resources/<id>/tmp`. Он передаётся через TEMP/TMP и JAVA_TOOL_OPTIONS (`java.io.tmpdir`), поэтому Gradle переиспользует только совместимый демон этой сессии. Кэши GRADLE_USER_HOME и зависимости остаются общими; параметры памяти проекта не заменяются. Простой Gradle-демона ограничен 15 минутами. Это не означает один JVM-процесс навсегда: другие версии Gradle/JDK и JVM-настройки могут создать дополнительные демоны той же сессии. Явная подмена этих переменных самим проектом может отключить разделение.

Старые общие Gradle-демоны при обнаружении работы на Tethium включаются только в общий бюджет; переносить их между персональными группами нельзя. Уже зарегистрированные через process_track отдельные сервисы включаются в бюджет владельца. Для других типов внешних общих демонов автоматическое разделение ещё не реализовано. Запущенные до обновления исполнители сохраняют окружение до следующего запуска.

Целевые проверки: `cpuControlProbe` — настоящий Windows-процесс, вложенный потолок 0,5% и сохранение группы после закрытия/повторного открытия управляющих дескрипторов; `sessionDaemonProbe` — настоящие Gradle-сборки A/B/A, разные PID между сессиями и повторное использование PID внутри сессии. `ResourceControlTest` проверяет сохранение/наследование настроек, принадлежность частного демона и исключение установщика/GUI/ядра из учёта задачи.

При первом переходе часть уже работающих процессов может находиться в несовместимых Windows Job Objects. Такие процессы невозможно перенести в общую иерархию без их нового запуска: диалог показывает полное число исключений и причины. Пока они остаются, потолок относится только к включённым процессам, а не ко всей старой нагрузке. Новые исполнители создают своё дерево внутри заранее закреплённой иерархии. Не останавливайте старые задачи автоматически ради миграции.


## Явная холодная миграция

Обычные обновления по-прежнему сохраняют исполняющиеся процессы. Только по явной просьбе пользователя `request_desktop_update.ps1 -RestartWorkloads` проводит холодную миграцию. Сначала требуется обычным горячим обновлением установить ядро с `restartProtocol=1`.

После проверки кандидата обновлятор сохраняет `restarts/<requestId>.json`: текущие задачи, очереди, паузы, автономию, расписания, последние результаты и PID со временем рождения. Затем отменяет исполнения и принудительно останавливает учтённые фоновые процессы; PID, успевший сменить владельца, не затрагивается. Ядро и хранитель CPU-групп запускаются заново. Через `/updates/restart/restore` прерванные задачи получают короткое сообщение «Сорян, перезапустились…» и ссылку на отдельный снимок контекста сессии. Сообщение продолжения ставится перед прежней очередью без изменения ручных пауз, черновиков и настроек автономии. Завершённые задачи не запускаются заново. Расписание дежурного, остановленное пользователем, остаётся остановленным.

Операции восстановления имеют отдельные ключи для каждой сессии и защищены от повторной доставки. При ошибке переключения тот же снимок используется для продолжения на предыдущем ядре. Это режим обслуживания с разрешённым пользователем прерыванием работы, а не новая политика обычных обновлений.


## Индикаторы машины и виджеты проекта

Под квотами показаны две строки CPU/RAM: Tethium / остальная система на ноутбуке с ядром. CPU включает задачи, зарегистрированных демонов, ядро, GUI и дочерние процессы браузера; общий лимит задач по-прежнему 85%. RAM Tethium — сумма приватной резидентной памяти, общие страницы остаются в части системы, чтобы не считать их несколько раз. Первый замер CPU требует двух наблюдений.

Проект рисует собственное содержимое двух независимых областей, записывая SVG в каталог `.tethium/` проекта (прежние имена `.tethium-widget-*.svg` в корне по-прежнему читаются):

- `.tethium/widget-bottom.svg` — узкая строка под обычным названием, на десктопе высота 11 px без дополнительного вертикального зазора. SVG может иметь собственный viewBox, например 142 × 16.
- `.tethium/widget-right.svg` — блок справа от текста на высоту обеих строк, на десктопе область 26 × 26 px с зазором 2 px от блока текста.

Можно задать один или оба файла. Никаких обязательных чисел, подписей, метрик или палитры: содержимое полностью задаёт SVG. Название/иконка проекта, раскрытие аккордеона и полоски ресурсов остаются общими. Десктоп и лёгкий клиент получают исходный SVG и рисуют его векторно с учётом масштаба экрана; сглаженная PNG остаётся для Android и совместимости. Доступ клиентов к репозиторию не нужен. Высота строки проекта на десктопе всегда 28 px; в свёрнутом проекте оба виджета скрыты.

Обновление файла подхватывается примерно за 2 секунды; без изменений SVG повторно не разбирается. Скрипт проекта должен записать временный файл и заменить целевой через atomic rename/replace. При ошибке сохраняется последнее корректное изображение, причина доступна в подсказке. Удаление файла убирает соответствующую область. `<title>` и `<desc>` используются для подсказки; допустим самодостаточный SVG до 256 КБ, внешние ресурсы и встроенный JS не исполняются. Динамику рисует скрипт проекта, обновляя файл.

Пример генератора H3Phoenix2: `C:/git/H3Phoenix2/tools/tethium_widgets.py`, разовый запуск `python tools/tethium_widgets.py`, наблюдение `python tools/tethium_widgets.py --watch`. Источники — `docs/progress/history.tsv`, `verified.tsv`, `target.tsv` и активные `gq.sh` задания. Подтверждённая метрика и прогноз без регрессий расположены снизу; справа число обработанных строк гейта. Серый круг 100% означает последний завершённый гейт, зелёный — выполняющийся. Матched prefix отказавшего proof в прогноз не входит.
