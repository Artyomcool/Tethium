# Работа над работающим Tethium

Пользователь работает в этом приложении. GUI и ядро живут в отдельных процессах; текущий агент исполняется ядром.

- Не заменяйте и не удаляйте файлы работающей сборки. Собирайте каждый кандидат в отдельный каталог: `gradlew.bat packageDesktop -PdesktopDestination=desktop-<изменение>-<дата>`.
- Если живые процессы запущены через `gradlew run` из `build/classes` и `build/resources`, изолируйте также Gradle `buildDirectory` через init-скрипт (`-I`), чтобы компиляция не меняла загруженные классы. Для отката сохраните отдельный пакет из фактически работающих классов и ресурсов и сверьте его `build` / `hostBuild` с `/health`.
- Для установки используйте `scripts/request_desktop_update.ps1 -AppPath <новый Tethium.exe> -SessionId <текущая сессия>`. Заявка сохраняется в `%LOCALAPPDATA%/Tethium/desktop-update-request.json`; один фоновый диспетчер вызывает `reload_desktop.ps1`. Последняя ожидающая заявка заменяет предыдущие, после перезапуска приложения незавершённая заявка возобновляется. Не создавайте цепочки одноразовых установщиков. Прямой `reload_desktop.ps1 -AppPath ... -PreviousAppPath ...` остаётся для проб и ручного восстановления. Фоновые процессы запускайте с `-WindowStyle Hidden`.
- Текущую версию проверяйте по `%LOCALAPPDATA%/Tethium/desktop-active.json`, живым процессам и дескрипторам в `clients/`. Не полагайтесь только на устаревший `pending.json`.
- Скрипт сначала проверяет новое ядро на согласованной копии SQLite без запуска агентов, затем запускает второй GUI, проверяет готовность через локальный IPC, переносит черновики и состояние окна и только после этого закрывает прежнее окно.
- При изменении только GUI ядро сохраняется. При совместимом `workerProtocol=1` новое ядро подхватывает независимые процессы запусков через их журналы в `workers/<runId>/`; завершения ответа ждать не нужно. Текст, вызовы инструментов, вопросы и Stop переживают замену ядра. Рабочей базой по-прежнему владеет только одно ядро; исполнители пишут отдельные журналы. Для первого перехода со старой версии или несовместимого протокола остаётся drain: дождаться только текущих запусков, сохранив очередь и пользовательские паузы. Не отменяйте текущий запуск ради обновления.
- Не запускайте второе ядро на рабочей базе одновременно с первым. `HostMain` владеет `host.lock`; кандидат до переключения проверяется на отдельной копии. Изменения схемы должны оставаться совместимыми с предыдущей версией для отката.
- После успешной установки диспетчер убирает за собой: копии базы в `updates/<id>/` кроме трёх последних обновлений (журналы остаются), профили браузера без живого процесса, пакеты `build/desktop-*` кроме пяти новейших, активного, собранных за последние два часа и используемых живыми процессами. Проверка: `scripts/probe_update_prune.ps1`. Вручную: `request_desktop_update.ps1 -PruneOnly`.
- Статус переключения — `.local/desktop-update/status.json`; журналы, копии базы и журнал первого перехода со старого ядра — `%LOCALAPPDATA%/Tethium/updates/<id>/`.
- По уточнению пользователя проверки должны быть короткими и целевыми. Не запускайте регрессионные UI-прогоны и полные наборы тестов без конкретной необходимости. Для точечной диагностики UI доступен `uxProbe`; для изменений самого протокола обновления — `scripts/probe_reload.ps1 -AppPath <сборка>`. Обычная установка использует встроенную проверку кандидата и готовности окна; повторять перед ней полный прогон обновления не нужно.
- Статус `waiting-for-runs` нужен только для первого перехода или несовместимого протокола. При `handoff` ядро меняется во время ответа; процессы исполнителей продолжают использовать свою исходную сборку, её файлы нельзя удалять до их завершения. В отчёте различайте уже заменённое окно и ещё ожидающее ядро.

Сессии работают с `danger-full-access` и `approvalPolicy=never` по решению пользователя; для исполнителя Claude это `--permission-mode bypassPermissions`. Исполнитель (Codex или Claude) задаётся выбором модели в шапке сессии и применяется со следующего запуска. Один проект использует общий каталог; worktree создаётся только по запросу пользователя.

При жалобах на скачки текста/прокрутки чата сначала поднимите накопленную диагностику: `python scripts/chat_layout_report.py --session <UUID> --minutes 10` (при известном времени — `--at <ISO-время-с-зоной>`). Исходные события GUI лежат в `%LOCALAPPDATA%/Tethium/diagnostics/chat-layout/*.jsonl`; в них есть причины рендера, геометрия, якоря, действия навигации и стеки перемещений. Не принимайте каждый автоматический скролл за дефект: сопоставьте его с `navigation.jump`, `navigation.setBottom`, восстановлением позиции и вводом пользователя. Журнал появляется только после запуска сборки с диагностикой.
